# Address search & normalization with fine-tuned embeddings

Semantic address normalization for Argentina: a user types a free-form address and the
system resolves it to the single canonical record it refers to — tolerating typos,
abbreviations, missing or reordered fields, and domain synonyms — by matching **fine-tuned
sentence embeddings** against an embedded master database.

## Why embeddings

The traditional approach to address matching is programmatic/rule-based, which is brittle:
every new spelling (`av.` vs `avenida`), typo, or field ordering needs another rule. Here,
matching is learned. Addresses are embedded into a vector space where "the same place,
written differently" lands close together, so the right canonical record can be retrieved by
nearest-neighbor search and ranked by similarity.

## How it works

The pipeline matches at several **field granularities** with models specialized per level
(province, locality/partido/municipio, street), each searched against the corresponding part
of the master database with its own similarity thresholds:

```
free-form query
   → preprocess / tokenize
   → embed (fine-tuned sentence-transformer, per field level)
   → nearest-neighbor vs. the embedded master DB (with abs/rel thresholds)
   → canonical record (normalized fields + coordinates)
```

Both a **structured** flow (fields provided separately) and an **unstructured** flow (one
free-text string) are supported.

## Fine-tuning: the contrastive dataset

The interesting part is how the training pairs are built. `src/train/` fine-tunes
Sentence-Transformers with **MultipleNegativesRankingLoss** (anchor–positive) and
**TripletLoss** (anchor–positive–negative). The dataset is generated by a family of
domain-specific augmentations (`src/train/preprocessing/finetuning_dataset.py`) that take a
real address and perturb specific fields, so the model learns what a valid match looks like:

- **Abbreviations** — e.g. `avenida` ↔ `av`, via a domain alias dictionary.
- **Keyboard typos** — realistic character-level noise.
- **Field / word masking** — dropping parts of the address.
- **Column shuffling** — reordering fields.

Errors are weighted differently depending on which field is changed, which is what encodes
"how wrong" a given perturbation is.

## Results

On the validation set, the fine-tuned embedding model reached a **false-positive rate of ~0.3%**, very few queries were confidently matched to the wrong canonical address. In practice this makes the search markedly more flexible and human than the previous rule-based matching (tolerant of typos, abbreviations, and partial or reordered input) while keeping wrong matches rare. Ubidata is now very close to taking it to production.

## Repository layout

```
configs/         YAML configs (base + per-model custom) for data, training, evaluation
src/
  preprocessing/ query preprocessing, embedding, master-DB handling
  train/         generic fine-tuner + contrastive dataset generation
scripts/         similarity-threshold analysis, model comparison, control tests
streamlit/       interactive demo UI
```

## Running

```bash
python -m venv venv && source venv/bin/activate
pip install -e .
```

Training and search are config-driven (YAML under `configs/`). Datasets, master database,
and model checkpoints are **not** included in this snapshot, so the configs point to local
paths that you would provide.
